# Miora declarations and signatures in bounded windows

Authorized scope: remove artificial transfer capacity gates while retaining bounded network frames and safe validation. Responsibility is architecture 8.3/8.7/8.8/8.13/8.14/8.15. The confirmed limit is Fastify's 2 MiB JSON frame when every asset declaration is sent together; raising it would only move the limit and increase allocation.

The existing intent store remains authoritative. A staged intent reserves one account/credit handoff and records expected item count; indexed manifest windows are appended transactionally and idempotently. Finalization requires every declared index. Until finalization, uploads, public imports and generation consumption are rejected. Conflicting declarations or counts fail explicitly. TTL is renewed through the existing retry lifecycle. No total asset count or byte-size business cap is introduced. The optional filename-200 and URL-4096 character gates are removed; media MIME, SHA-256, safe-integer size and source-host checks remain.

The additive API is `POST /v1/upload-intents/staged`, `PUT /:id/manifest {offset,assets}`, `POST /:id/finalize`, `GET /:id/status`, `GET /:id/items?offset&limit`, and `POST /:id/complete?summary=true`. Ordinary manifest windows retain a finite per-frame body budget; a single oversized scalar automatically uses `/manifest-stream`, whose isolated raw parser checks current RAM and native JS representation capacity while receiving chunks, with an inactivity watchdog and unchanged schema/owner checks, rather than a fixed scalar/frame quota. Status uses database aggregates and one safe failed-item summary; signature pages stay small. Public import execution loads pending windows instead of the full manifest. Existing clients/routes remain compatible.

Desktop clients select this protocol for declarations larger than 512 KiB or an existing staged checkpoint, hash the manifest incrementally with the same canonical bytes, persist the intent before appending and replay identical windows after interruption. They obtain only the next three signatures (matching existing PUT concurrency), complete individual items with small summaries and poll aggregate status. Existing terminal/retryable error interpretation, cancellation, role selection and user-authored COS diagnostics remain in place. An older server lacking staged routes reports an explicit unsupported failure for a large declaration; it cannot silently downgrade to a frame it cannot receive.

No production deployment/configuration, credentials, actual media upload or paid generation is used for validation. Targeted database/API and fake-client tests cover >2 MiB aggregate declarations, missing windows, conflicts, repeats, owner mismatch, signatures, checkpoints and safe failures. Local success does not establish a production root cause.

Active staged signing/status reads renew the existing 15-minute preparation lease, so a sequence of valid windows is not cut off by an aggregate elapsed-time cap. Single signed PUTs keep their actual STS validity and existing cancellation/timeout budget. A source-fetch TypeError caused by an already-aborted caller signal was demonstrably misclassified as transient; retry now checks the caller signal and reports `TRANSFER_CANCELLED` without re-reading sources. This is a local contract fix, not a claim about historical live failures.

Background execute/resume now enters the service's existing diagnostic context by job ID, including startup recovery. Diagnostics flush after business shutdown even when shutdown throws. Optional isolated journald namespace examples in `server/deploy` provide explicit rotation/retention without changing a host or global journal policy; they remain uninstalled.

Remaining outside this module: very large generation-job prompt/options bodies and staged-create options still use their existing 2 MiB inline routes. Existing Miora client preparation/PUT timeout policy is unchanged. These are not claimed to have been removed by declaration pagination.
