# Miora upload intents

For a large declaration, use the additive staged protocol: `POST /v1/upload-intents/staged {idempotencyKey,assetCount,options}`, indexed `PUT /:id/manifest {offset,assets}` windows, then `POST /:id/finalize`. Ordinary manifest frames are bounded to 1 MiB, with no total item-count/size quota. A single oversized scalar automatically uses `PUT /:id/manifest-stream`, which reads chunks under current process/machine memory admission instead of a fixed body/scalar quota. Missing indices block finalization/consumption; conflicting retries fail. `GET /:id/items?offset&limit` signs only a bounded page, `POST /:id/complete?summary=true` returns a small aggregate, and `/status` returns counters and one safe failure. Existing inline routes remain compatible. Active staged preparations renew the existing lease; a large overall transfer is not limited to its initial 15-minute lease.

Use `GET /:id/diagnostics?offset&limit` for a **pure read** of owned intent status/errors with creation/observation times and the current request ID. It never renews, signs or resumes imports and never exposes source URLs or credentials. Client task correlation remains in the existing checkpoint. The original `GET /:id` and `/status` may resume imports; do not call them for a side-effect-free production investigation. New endpoints and the optional Studio-only journal rotation examples have not been deployed by this work.

Backend diagnostics use the existing service logger, with fixed `miora.*` events and bounded asynchronous buffering. Correlate `requestId`, `apiRequestId`, `uploadIntentId`, `itemIndex` and provider `taskId`; transfer events distinguish source fetch/read/hash verification, COS grant, PUT response, retries and final outcome. This transfer uses a single streaming PUT, so there are no multipart-init/part/complete events. Provider errors retain only bounded codes and COS request IDs. Source identity hashes the origin/path and excludes the signed query; neither source/object locations, credentials nor bodies are logged.

For a real failure investigation, provide UTC time window, client task ID, intent ID/item index and the safe `error` fields returned by `GET /v1/upload-intents/:id`. If intent creation failed, provide its request ID and HTTP/application code. Capture the matching service events from `journalctl -u aistudio-studio.service --utc --since ... --until ... --no-pager`; don't replay paid jobs or upload private media to reproduce a failure. Repository installation sends stdout to systemd's journal. Its actual disk budget/retention belongs to the existing host journald configuration and has not been verified in this workspace; operators can inspect it with `systemd-analyze cat-config systemd/journald.conf` and `journalctl --disk-usage`. Keep finite journal size and retention under the host's existing policy; this feature creates no second log file and does not change production configuration. `miora.diagnostics.dropped` reports local queue overflow/sink failures.

The managed video gateway prepares Miora references before it creates a paid generation job.

- `POST /v1/upload-intents` selects and pins one enabled Miora account.
- Hash-verified public imports are reused by account, SHA-256, size, MIME type and media kind. Direct client PUTs are not added to the cross-task cache because the server cannot independently prove their content hash.
- Public HTTPS media from `MIORA_PUBLIC_MEDIA_HOSTS` is streamed into the account's Tencent COS prefix.
- Public imports are bounded across the service and per account. Concurrent intents for the same account and verified media identity share one in-flight transfer; a finished or failed flight is removed, so later retries are independent.
- Source fetch, COS grant and COS PUT retry only explicit transient network failures, HTTP 408/425/429 and 5xx with finite backoff. Size/hash/policy failures remain terminal for that attempt.
- Failed public items retain a safe typed error (`stage`, `reason`, `retryable`, optional HTTP/network code) without source URLs, signed URLs, cookies or credentials. Repeating `POST /v1/upload-intents` with the same idempotency key and identical manifest resumes only failed public items in the same intent. `GET /v1/upload-intents/:id` never resets failed items or issues direct-upload signatures; it may continue already-importing public items so service restarts remain recoverable.
- Local-only media receives a ten-minute PUT request signed for one exact object, MIME type and byte length.
- Upload intents do not impose a gateway-specific per-file size or reference-count ceiling. Sizes must be positive safe integers and completion indexes nonnegative safe integers; the selected platform model determines which references it accepts. The existing small JSON request-body budget remains, independent of media bytes streamed or uploaded directly to COS.
- Each signed PUT fixes its COS key from that exact STS grant; a later grant may use a different prefix. `POST /v1/upload-intents/:id/complete` records the trusted client's successful PUT, and direct uploads are not placed in the cross-task cache.
- `GET /v1/upload-intents/:id` reports preparation status.
- `POST /v1/jobs` with `uploadIntentId` persists and owns one deterministic gateway job before consuming the intent. Repeating it returns that job; it never recreates a pruned paid job.

Miora credentials and STS secrets never leave the server. Legacy `/v1/assets` remains available for older clients and other adapters.

The legacy multipart upload resource budget (`MAX_UPLOAD_BYTES`) remains separate: it protects server-buffered uploads and is not applied to direct COS intent declarations. Authentication, intent ownership, manifest equality, trusted public-source hosts, streamed hash/length verification, and authorization expiry are unchanged.
